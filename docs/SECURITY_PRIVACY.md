# Security and Privacy Contract

The service processes untrusted files from the public internet. File conversion is therefore a hostile-input workload.

## Security objectives

- a user file cannot execute arbitrary code or commands
- one user's job cannot read another user's workspace
- one expensive file cannot exhaust the entire service
- malformed files fail within bounded resources
- secrets and access tokens do not reach workers unless strictly required
- the control plane remains functional if a worker crashes
- files are not retained longer than necessary
- operational telemetry does not become a shadow copy of user content

## Threat model

Relevant threats include:

- parser/codec vulnerabilities
- crafted images and PDFs
- decompression bombs
- huge pixel dimensions
- pathological video duration/resolution/codec structures
- malicious filenames and path traversal
- shell/argument injection
- zip/archive bombs if archives are added later
- resource exhaustion
- repeated callbacks and replay
- Telegram update redelivery
- worker crashes and partial outputs
- disk exhaustion
- cross-job file leakage
- sensitive data leakage through logs
- stale temporary files

## Command execution policy

User-controlled text must never be concatenated into shell commands.

Preferred execution model:

- invoke known binaries directly without a shell
- fixed executable path/image
- fixed operation implementation
- allowlisted arguments generated by trusted code
- parameters validated against a typed bounded schema

No endpoint, bot command, callback, or Mini App input may provide:

- executable name
- arbitrary argv
- shell string
- script body
- filesystem path outside the job workspace
- output destination outside the job workspace

## File identity and validation

Filename extensions and client MIME types are advisory only.

The service should:

- generate an internal filename/object id
- inspect magic bytes/container structure
- decode/probe using the relevant bounded tool
- compare detected type with operation requirements
- validate output independently before upload

Original names may be used when constructing a friendly download name, but should not determine paths or execution behavior.

## Worker isolation

Conversion workers should be separate from the Telegram gateway.

Target controls:

- unprivileged user
- no host filesystem access beyond mounted job workspace
- no Docker socket
- no secrets unrelated to the operation
- restricted or disabled network
- CPU quota
- memory limit
- process count limit
- file size/disk quota
- hard timeout

A worker crash should fail only the current attempt/job.

## Resource limits

Limits must be explicit configuration, including:

- input bytes
- aggregate bytes
- image width/height/pixel count
- PDF page count
- video duration
- output bytes
- files per collection
- concurrent jobs per user
- global worker concurrency
- timeout by operation/resource class

No advertised operation is considered safe until its worst meaningful resource dimensions have bounds.

## Temporary file lifecycle

Expected lifecycle:

receive -> validate -> process -> validate output -> upload -> expire/delete

Requirements:

- every workspace has a TTL
- normal completion schedules deletion
- failure schedules deletion
- abandoned workspaces are reaped
- cleanup failures produce metrics/alerts
- backups must not accidentally capture temporary user content

The initial target is short-lived storage measured in minutes/hours, not days.

## Runtime singleton

The public polling runtime is singleton-controlled through a Redis lease.

Requirements:

- only the current lease owner may perform startup recovery, run the queue worker,
  execute retention/diagnostics loops, or start Telegram polling;
- lease acquisition waits for a bounded handoff interval during deployments;
- renewal and release are owner-token checked;
- a stale process cannot renew or delete a newer owner's lease;
- lease loss fails closed by cancelling the owned runtime;
- the app remains configured for one production replica; the lease is defense in
  depth against deployment overlap and accidental duplicate instances.

## Privacy

The service should retain only metadata needed for operation and product reliability.

Allowed durable examples:

- pseudonymous Telegram user/chat identifiers where operationally necessary
- job id
- operation id/version
- timestamps
- input/output byte counts
- processing duration
- state
- stable error code
- resource measurements

Avoid durable storage of:

- file contents
- full extracted metadata
- original filenames when not required
- captions/message bodies unrelated to the operation
- thumbnails generated only for processing

A public privacy notice must accurately state retention behavior before public launch.
The current public-MVP policy automatically reaps terminal job records and
Telegram update receipts after seven days; active jobs are preserved. Bounded
production recovery snapshots can temporarily retain older copies after live
deletion and must be disclosed separately. See `docs/PRIVACY.md`,
`docs/RETENTION.md`, and `docs/RAILWAY.md`.

## Logging

Never log:

- bot token
- full request Authorization headers
- file contents
- arbitrary binary metadata dumps
- absolute temporary paths containing sensitive source names

Prefer stable ids and error classes.

Production logging must pass through a final redaction layer after exception
traceback formatting. The redactor must remove configured secrets, Telegram bot
tokens, PostgreSQL/Redis URLs, Authorization values, provider file paths, and
filename/file-path fields even when they originate inside third-party exception
messages.

Redaction is defense in depth. Application code should still avoid placing
sensitive values in log messages in the first place.

## Abuse protection

The MVP requires:

- per-user rate limits
- per-user concurrency limits
- global concurrency cap
- size limits before materialization where possible
- rejection before expensive work
- bounded queue retention
- cancellation/expiry for stale jobs

Rate limits are protection controls, not monetization controls.

## Dependency security

Native tools such as FFmpeg, image codecs, and PDF parsers are part of the attack surface.

Requirements:

- pinned/reproducible runtime images
- routine security updates
- minimal packages in worker images
- dependency vulnerability monitoring
- regression corpus for malformed inputs
- ability to disable an operation independently if a dependency becomes unsafe

## Security release gate

Public launch is blocked if any of the following is true:

- workers execute with broad host privileges
- user data can influence arbitrary shell execution
- a malformed input can kill the gateway
- job workspaces are shared without isolation
- resource limits are absent
- cleanup is best-effort without detection
- unknown file types are accepted by extension alone
- secrets appear in logs/tests/artifacts
