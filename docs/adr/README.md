# Architecture Decision Records

Use ADRs for decisions that materially change:

- component boundaries
- persistent state semantics
- security/trust boundaries
- job execution model
- file retention/storage model
- transport model
- major runtime/dependency choices

Naming:

`NNNN-short-kebab-title.md`

Each ADR should include:

- Status
- Context
- Decision
- Consequences

Do not rewrite accepted ADR history to make later decisions appear inevitable. Supersede an old ADR with a new one and link them.
